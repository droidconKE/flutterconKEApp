# Architecture

*Last verified: 2026-09-11, against `feat/2026_rebrand`.*

## Layering

```
lib/
  main_development.dart / main_staging.dart / main_production.dart   # 3 entrypoints, one per flavor
  bootstrap.dart          # shared startup sequence + MultiBlocProvider wiring
  app.dart                # MaterialApp.router, theme, notification listener wiring
  firebase_options.dart   # generated by flutterfire CLI

  core/
    di/injectable.dart    # get_it + injectable bootstrap
    theme/                # AppTheme, ThemeColors

  common/
    data/
      models/             # freezed remote DTOs (session.dart, speaker.dart, sponsor.dart, feed.dart, ...)
      models/local/       # isar_community collections (local_session.dart, local_speaker.dart, ...)
      enums/
    repository/           # ApiRepository, AuthRepository, DBRepository, FirebaseRepository,
                           # HiveRepository, ShareRepository — all @singleton
    utils/                 # NetworkUtil, FlutterConRouter, NotificationService, flavor_config, etc.
    widgets/               # shared widgets (app bar, bottom nav, ...)

  features/<feature>/
    cubit/                # flutter_bloc Cubits + freezed states
    ui/                   # screens
    widgets/               # feature-local widgets

  l10n/                   # generated AppLocalizations + arb source
  versioning/              # generated build_version.dart (via build_version builder)
```

Features present: `about`, `auth`, `dashboard`, `feed`, `feedback`, `home`, `sessions`, `splash`.
`home` contains sponsors/organisers/speakers-related cubits despite the name — it is effectively the
first dashboard tab's data layer, not a single narrow "home screen" concern. Check `lib/features/home/cubit/`
before assuming a piece of data belongs to a differently-named feature.

## Dependency injection

`lib/core/di/injectable.dart` + generated `lib/core/di/injectable.config.dart`. `configureDependencies()`
calls `getIt.initGetIt()` then `await getIt.allReady()`, invoked once in `bootstrap.dart` before anything
else runs.

Every DI-registered class is `@singleton`, constructed with **no arguments** — each one internally
constructs whatever it needs (e.g. `NetworkUtil()` inside `ApiRepository`, `FirebaseAuth.instance` inside
`AuthRepository`). There are currently no `@injectable` (factory-scoped) bindings and no manual bindings
in the empty `@module abstract class RegisterModule {}` placeholder. The full registered set:

| Type | File |
|---|---|
| `ApiRepository` | `lib/common/repository/api_repository.dart` |
| `AuthRepository` | `lib/common/repository/auth_repository.dart` |
| `DBRepository` | `lib/common/repository/db_repository.dart` |
| `FirebaseRepository` | `lib/common/repository/firebase_repository.dart` |
| `HiveRepository` | `lib/common/repository/hive_repository.dart` |
| `ShareRepository` | `lib/common/repository/share_repository.dart` |
| `NotificationService` | `lib/common/utils/notification_service.dart` |
| `FlutterConRouter` | `lib/common/utils/router.dart` |

**Cubits are outside the DI graph entirely.** Adding a new Cubit means adding a `BlocProvider` entry to
the `MultiBlocProvider` list in `bootstrap.dart`, pulling its repository dependencies via `getIt()` at
construction time — not annotating the Cubit itself. If a new Cubit needs a repository, register the
repository with `@singleton` (if it isn't already) and pass it via `getIt()` in `bootstrap.dart`.

## State management

`flutter_bloc` Cubits (not full Blocs — no repo code uses `Bloc`/events, only `Cubit` + methods). Each
feature's `cubit/` directory holds one Cubit per unit of work (e.g. `FetchSessionsCubit`,
`BookmarkSessionCubit`, `FetchGroupedSessionsCubit` all coexist under `features/sessions` and
`features/home`), each with a freezed sealed state class (typically `Initial` / `Loading` / `Loaded` /
`Error` variants). `AppBlocObserver` (`bootstrap.dart`) logs every Cubit state change and error via
`dart:developer`'s `log()` — check there first when debugging "why didn't the UI update."

There is no app-wide store beyond what's provided at the root `MultiBlocProvider` in `bootstrap.dart` —
roughly 15 Cubits are constructed and provided there at startup, all living for the app's lifetime (none
are scoped to a route/subtree).

## Bootstrap sequence

`bootstrap.dart`'s `bootstrap(builder)` function, called from each `main_<flavor>.dart` after that
entrypoint sets up `FlutterConConfig` (see [build-and-ci.md](build-and-ci.md) for flavor details):

1. `Bloc.observer = const AppBlocObserver()`
2. `Firebase.initializeApp(...)`
3. `configureDependencies()` — get_it/injectable wiring
4. `getIt<HiveRepository>().initBoxes()`
5. `localDB = await getIt<DBRepository>().init()` — opens the Isar instance, assigned to the
   module-level global `Isar localDB` in `injectable.dart` (not itself part of the DI container)
6. `NotificationService` permission request + init
7. `FirebaseRepository.init()` (remote config)
8. `runApp(MultiBlocProvider(providers: [...], child: await builder()))`

Errors during steps 1–7 are caught: in debug mode they're just logged; in release mode
`FlutterError.onError` / `PlatformDispatcher.instance.onError` are wired to report to Firebase
Crashlytics instead. A bootstrap failure does not show any fallback UI — if `runApp` is never reached,
the app stays on whatever the platform's default blank/splash surface is.

## App shell

`lib/app.dart`'s `MyApp` wraps the tree in `Sizer` (responsive sizing helper) and returns
`MaterialApp.router` with:
- `themeMode`: read once from `HiveRepository.retrieveThemeMode()` at construction time — not reactive;
  changing the persisted theme mode elsewhere will not repaint `MaterialApp` without an explicit rebuild
  trigger (there is none currently wired for this).
- `theme` / `darkTheme`: `AppTheme.lightTheme()` / `AppTheme.darkTheme()` (`lib/core/theme/theme_data.dart`)
- `routerConfig`: `getIt<FlutterConRouter>().config()`
- `AwesomeNotifications().setListeners(onActionReceivedMethod: ...)` wired in `initState` — see
  [notifications.md](notifications.md)
